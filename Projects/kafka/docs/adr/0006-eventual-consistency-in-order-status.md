# OrderStatusService tolerates out-of-order events instead of buffering

Kafka guarantees ordering within a single topic-partition, not across topics — so OrderStatusService, which fans in from 6 independently-partitioned topics, can observe (say) a `PaymentApprovedEvent` before the `OrderPlacedEvent` for the same `orderId`. We chose to handle this by creating a placeholder `OrderStatus` record (`items: []`, `totalAmount: 0`) the first time *any* event for an `orderId` arrives, appending to its timeline regardless of arrival order, and backfilling `items`/`totalAmount` once `OrderPlacedEvent` is consumed — rather than buffering events until `OrderPlacedEvent` arrives and hiding the order until then. The UI may briefly show a card with "0 items" before it catches up; we accept this because it makes the pipeline's real eventual-consistency behavior visible rather than papering over it, and it avoids the added complexity of an out-of-order buffer. `GET /orders/{id}` returns `404 Not Found` for both a truly unknown `orderId` and one whose events simply haven't been consumed yet — the API does not distinguish the two, since the Blazor UI never needs to (it learns of new orders via the SignalR push, not by polling).
