# Backorder is all-or-nothing, not per-item

An Order can contain multiple Items, and real inventory systems often support partial fulfillment — reserving what's available and backordering the rest as a split shipment. We chose **all-or-nothing** instead: if any Item in the Order is unavailable, `InventoryBackorderEvent` is published for the whole Order and nothing is reserved. This keeps `InventoryReservedEvent`, `OrderShippedEvent`, and every downstream consumer working with exactly one Shipment per Order, with no split-shipment or partial-payment-adjustment logic to model. The trade-off is realism — a real e-commerce system would very likely support partial fulfillment — but that complexity doesn't teach anything new about Kafka itself (still just topics, keys, and consumer groups), so it isn't worth the added event/schema surface for this demo.
